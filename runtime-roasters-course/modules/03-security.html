Secure Gates & Roles

How Runtime Roasters protects public data and limits administrative access.

Gatekeepers: API Gateway & Casbin

In a microservice system, not all APIs should be exposed to the public. For example, customers should query trace info, but only store managers should view invoice logs.

We use KrakenD API Gateway as the front door. It routes public requests but hides internal microservice URLs. To verify *who* can do *what*, we use Casbin.

The Concert Metaphor

🎟️
Front Gate (KrakenD)

Checks if you have a valid general ticket (authentication token). If you don't, you can't enter.

🕶️
VIP Section Guard (Casbin RBAC)

Checks your specific pass. Only people with "Backstage Store Manager" badges are allowed in.

The Access Policy Matcher

Let's look at the frontend Casbin configuration model. It defines how the system matches a user's role (the subject) against the requested URL (the object) and action:

CASBIN MODEL 
[request_definition]
r = sub, obj, act

[matchers]
m = (r.sub == 'ADMIN') || \
  ((r.sub == p.sub || g(r.sub, p.sub)) && \
   keyMatch(r.obj, p.obj) && \
   regexMatch(r.act, p.act))
PLAIN ENGLISH

Define a request request template: Who (subject), What (object), Action (read/write).

Let's check if the rule matches. The backslashes allow splitting the formula over lines.

If the user role is ADMIN, let them in immediately with no further checks.

Otherwise, check if user matches the policy role directly OR inherits it (e.g. manager inherits staff).

Check if the requested URL matches the resource path defined in our policy (e.g. `/v1/sales/*`).

Check if the action (GET/POST/DELETE) matches the allowed action pattern.

💡
Vibe Coder Insight: Declare, Don't Hardcode

Why write a policy model instead of standard if (role == "manager") checks in the code? Declaring policies in Casbin means you can change roles and paths in a configuration file without rewriting and redeploying your codebase. This makes scaling authorization policies extremely simple.
