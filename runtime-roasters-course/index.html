The Lineage Query

Let's look at the actual Go code in the trace-service usecase that aggregates this trace data. We first look up the retail item, then fetch all the upstream events associated with that batch.

GO CODE 
func (s *Service) GetPublicTrace(ctx context.Context, traceCode string) (*PublicTraceDocument, error) {
  item, err := s.retail.GetSoldItem(ctx, traceCode)
  if err != nil {
    return nil, err
  }
  events, err := s.findLineageEvents(ctx, item.SourceBatchID, item.SourceHarvestID)
  if err != nil {
    return nil, err
  }
  return &PublicTraceDocument{
    ProductID: item.ProductID,
    TraceCode: item.TraceCode,
    OriginBatchID: item.SourceBatchID,
  }, nil
}
PLAIN ENGLISH

Define a function that takes a trace code and returns the complete trace document.

Call the retail service over HTTP/gRPC to get the sold item info for this cup.

If the retail service returns an error (e.g. cup doesn't exist), fail immediately.

No error? Proceed to find the farm batch and harvest event lineage in the database.

If fetching events fails, return that error instead of half-baked details.

Return a brand new trace document containing the customer cup details and the bean lineage!

💡
Vibe Coder Insight: Data Separation

Notice that we don't store everything in one massive database. The customer's purchase lives in retail-service, while the farm harvests live in the trace logs database. A microservice architecture fetches data dynamically from multiple places rather than centralizing it, which helps keep the services independent and fast.

Module 3

Secure Gates & Roles

How Runtime Roasters protects public data and limits administrative access.

Gatekeepers: API Gateway & Casbin

In a microservice system, not all APIs should be exposed to the public. For example, customers should query trace info, but only store managers should view invoice logs.

We use KrakenD API Gateway as the front door. It routes public requests but hides internal microservice URLs. To verify *who* can do *what*, we use Casbin.

The Concert Metaphor

🎟️
Front Gate (KrakenD)

Checks if you have a valid general ticket (authentication token). If you don't, you can't enter.

🕶️
VIP Section Guard (Casbin RBAC)

Checks your specific pass. Only people with "Backstage Store Manager" badges are allowed in.

The Access Policy Matcher

Let's look at the frontend Casbin configuration model. It defines how the system matches a user's role (the subject) against the requested URL (the object) and action:

CASBIN MODEL 
[request_definition]
r = sub, obj, act

[matchers]
m = (r.sub == 'ADMIN') || \
  ((r.sub == p.sub || g(r.sub, p.sub)) && \
   keyMatch(r.obj, p.obj) && \
   regexMatch(r.act, p.act))
PLAIN ENGLISH

Define a request request template: Who (subject), What (object), Action (read/write).

Let's check if the rule matches. The backslashes allow splitting the formula over lines.

If the user role is ADMIN, let them in immediately with no further checks.

Otherwise, check if user matches the policy role directly OR inherits it (e.g. manager inherits staff).

Check if the requested URL matches the resource path defined in our policy (e.g. `/v1/sales/*`).

Check if the action (GET/POST/DELETE) matches the allowed action pattern.

💡
Vibe Coder Insight: Declare, Don't Hardcode

Why write a policy model instead of standard if (role == "manager") checks in the code? Declaring policies in Casbin means you can change roles and paths in a configuration file without rewriting and redeploying your codebase. This makes scaling authorization policies extremely simple.

Event-Driven Flow

How Kafka and WebSockets stream updates to dashboards in real-time.

Publish & Subscribe

When operations occur (like warehouse dispatching or driver GPS moving), we want the manager dashboard to update instantly. We do this using an event-driven flow.

The service that processes the action publishes an event to Kafka. Other services can subscribe to this stream and process events asynchronously.

Real-Time Streaming

To get these events from Kafka to the customer's web browser, we use a WebSocket. WebSockets keep a persistent connection open, letting the server push data instantly without the browser needing to refresh.

The Go Send Pump

This Go function in the socket-service continuously listens to a Go channel (a queue of messages) and writes them to the browser's WebSocket:

GO CODE 
func (s *Service) writePump(client *Client) {
  defer client.cancel()
  for body := range client.send {
    err := client.conn.WriteMessage(websocket.TextMessage, body)
    if err != nil {
      return
    }
  }
}
PLAIN ENGLISH

Define the writePump method which handles sending messages to a single client.

Ensure the client's context is canceled and cleaned up when this function exits.

Start a loop that waits for new data packets arriving in the client's send channel.

Write the data block directly into the WebSocket connection as a text message.

If writing fails (e.g. the customer closed their browser tab), exit the function.

End of the loop and clean shutdown code.

💡
Vibe Coder Insight: Don't Poll, Push!

In traditional web design, apps query the server every 5 seconds ("polling") to check for changes. This wastes CPU and network bandwidth. WebSockets allow the server to push messages ONLY when something actually happens, reducing server load and making updates instant.

Module 5

Real-Time Driver GPS

How Valkey tracks delivery driver locations in real-time using geospatial coordinates.

Geospatial Querying

When driver locations are constantly changing, writing them to a standard SQL database like PostgreSQL creates massive write overhead. Instead, we use Valkey.

Valkey has native support for geospatial indexes, which makes it extremely efficient to store GPS positions and quickly query which drivers are closest to a retail store.

The Push-Pin Metaphor

📍
Putting Pins on the Board

Every time a driver sends a GPS coordinate, it is like pinning their location on a grid board. Valkey keeps this board entirely in system memory for instant lookups.

⚡
Drawing a Circle search

To find nearby drivers, the server asks Valkey: "Find all driver pins within a 5-mile radius of Store A." Valkey computes this in milliseconds.

The Location Saver

Let's look at the Go implementation in the logistics-service. It saves the driver's coordinates and updates their "last seen" timestamp in Valkey:

GO CODE 
func (s *Service) storeDriverLocation(ctx context.Context, driverID string, lat float64, long float64) error {
  err := s.rdb.GeoAdd(ctx, driverLocationsKey, &redis.GeoLocation{
    Name:      driverID,
    Longitude: long,
    Latitude:  lat,
  }).Err()
  if err != nil {
    return err
  }
  return s.rdb.Set(ctx, "driver:last_seen:"+driverID, time.Now().Format(time.RFC3339), 90*time.Second).Err()
}
PLAIN ENGLISH

Define a helper function that takes the driver ID, latitude, and longitude, and saves them.

Call the Valkey GeoAdd command to store the driver's ID and coordinates under the geospatial index key.

Provide the specific longitude first, then the latitude matching Valkey's coordinate standard.

Check if the Valkey Geospatial operation returned an error. If so, fail immediately.

No error? Set a standard key-value entry with a 90-second expiration to track when we last heard from the driver.

Return nil (no error) to indicate the driver location was successfully recorded.

💡
Vibe Coder Insight: Expiring Keys

Valkey allows you to set a "Time to Live" (TTL) on any key (e.g. 90*time.Second). Once that time expires, Valkey deletes the key automatically. This is perfect for heartbeats — if a driver's phone loses signal or battery dies, the driver disappears from the active dashboard map automatically because their "last_seen" key expires.

Module 6

Inbox/Outbox Reliability

How Runtime Roasters uses transactional inbox/outbox patterns to prevent dual-write failures.

The Dual-Write Problem

In a microservice system, when you complete a sale, you must update the database AND publish an event to Kafka. But what happens if the database update succeeds, and then the power cuts out before publishing the message to Kafka?

Your systems are now out of sync — a "dual-write failure". To prevent this, we use the Transactional Outbox Pattern.

The Double-Entry Metaphor

🖋️
Atomic Commit

Just like double-entry bookkeeping, we write both the order log and the message-to-be-sent into the database in one single transaction.

🔄
Relay Service

A separate process scans the database for unsent outbox messages and publishes them to Kafka safely. If publishing fails, it retries.

The Atomic Database Transaction

Let's look at the Go implementation in the retail-service. In one single, atomic transaction block, we create the order and the outbox event record:

GO CODE 
err = s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
  if err := tx.Create(order).Error; err != nil {
    return err
  }
  return tx.Create(outbox).Error
})
PLAIN ENGLISH

Begin a database transaction block. Everything inside this block must succeed together, or fail together.

Try to insert the new order record into the database table.

If creating the order fails, return the error immediately to abort (rollback) the transaction.

Insert the outbox event record containing the Kafka payload into the outbox events table.

Return from the transaction. GORM commits the transaction if this function returns nil.

End of the GORM database transaction block.

💡
Vibe Coder Insight: What is Atomicity?

In databases, atomicity ensures that you never end up in a half-finished state. If the server crashes after inserting the order but before inserting the outbox event, the database rolls back the order insert, ensuring clean data integrity.
