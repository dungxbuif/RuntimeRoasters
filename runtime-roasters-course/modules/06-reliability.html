Inbox/Outbox Reliability

How Runtime Roasters uses transactional inbox/outbox patterns to prevent dual-write failures.

The Dual-Write Problem

In a microservice system, when you complete a sale, you must update the database AND publish an event to Kafka. But what happens if the database update succeeds, and then the power cuts out before publishing the message to Kafka?

Your systems are now out of sync — a "dual-write failure". To prevent this, we use the Transactional Outbox Pattern.

The Double-Entry Metaphor

🖋️
Atomic Commit

Just like double-entry bookkeeping, we write both the order log and the message-to-be-sent into the database in one single transaction.

🔄
Relay Service

A separate process scans the database for unsent outbox messages and publishes them to Kafka safely. If publishing fails, it retries.

The Atomic Database Transaction

Let's look at the Go implementation in the retail-service. In one single, atomic transaction block, we create the order and the outbox event record:

GO CODE 
err = s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
  if err := tx.Create(order).Error; err != nil {
    return err
  }
  return tx.Create(outbox).Error
})
PLAIN ENGLISH

Begin a database transaction block. Everything inside this block must succeed together, or fail together.

Try to insert the new order record into the database table.

If creating the order fails, return the error immediately to abort (rollback) the transaction.

Insert the outbox event record containing the Kafka payload into the outbox events table.

Return from the transaction. GORM commits the transaction if this function returns nil.

End of the GORM database transaction block.

💡
Vibe Coder Insight: What is Atomicity?

In databases, atomicity ensures that you never end up in a half-finished state. If the server crashes after inserting the order but before inserting the outbox event, the database rolls back the order insert, ensuring clean data integrity.
